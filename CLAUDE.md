# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Gratitude is a personal iPhone app (SwiftUI + SwiftData) for a twice-daily mindfulness check-in: a short adaptive Q&A right after waking and right before bed, plus an on-demand "Reflect" mode that resurfaces a specific past day (morning and evening together, plus any photo) to revisit, spotlighted front-and-center rather than as a list. Local-first storage, with an optional client-side-encrypted backup to the user's own private CloudKit database. Evening check-ins also let you tag a response with a person and send them a "Smile" ("send a smile" is the app's verbiage throughout) — the one feature in this app that involves another person's device (see "Smiles" below). If that day's evening check-in had a tagged person, Reflect offers a one-click resend of the same smile without re-running the contact picker. See `README.md` for the product/setup overview.

## Commands

Build for the simulator from the CLI (no test target is wired up with real tests yet — `gratitudeTests`/`gratitudeUITests` are unmodified Xcode template stubs):

```bash
# List available simulators (needed once to get a destination id/name)
xcrun simctl list devices available

# Build
xcodebuild -project gratitude.xcodeproj -scheme gratitude \
  -destination 'platform=iOS Simulator,id=<SIMULATOR-ID>' build

# Install + launch after a build, to sanity-check it boots
xcrun simctl install <SIMULATOR-ID> <path-to>/gratitude.app
xcrun simctl launch <SIMULATOR-ID> com.sachabest.gratitude
xcrun simctl io <SIMULATOR-ID> screenshot out.png
```

This repo also has the `ios-simulator` MCP server configured (`.mcp.json`) for interactive testing — screenshotting, tapping, typing, swiping through real flows instead of only reading code. Its `ui_tap`/`ui_swipe`/`ui_type`/`ui_describe_all` tools need Facebook's `idb` client on `PATH`; see README.md's "Interactive Simulator testing" section for how it's set up (`idb-companion` via Homebrew, `idb` itself pinned in `tools/idb/` via `uv`, symlinked onto `PATH`). Always pull tap coordinates from `ui_describe_all`'s `AXFrame` (already in the same point-space `ui_tap` expects) rather than eyeballing a screenshot — screenshots are pixel space at a different scale (e.g. 1206×2622 px vs. 402×874 pt on iPhone 17) and guessed coordinates miss.

The `gratitude` folder is a **PBXFileSystemSynchronizedRootGroup** in the Xcode project — any `.swift` file added anywhere under `gratitude/gratitude/` is automatically picked up by the target. Never hand-edit `project.pbxproj` to add source files.

## Architecture

### Data model (SwiftData, `Models/`)

- `CheckIn`: one morning or evening entry for a given calendar day. `date` is always normalized to `Calendar.current.startOfDay(for:)` — every date comparison in the codebase (today lookups, streaks, the date-nav header) relies on comparing already-normalized `Date` values with plain `==`, not calendar-aware equality checks.
- `QuestionResponse`: one answer, cascade-deleted with its `CheckIn`. Stores a *snapshot* of the question text and `answerKindTag` at the time it was answered, independent of the live `QuestionBank` content, so past entries stay legible even if question wording changes later.
- `Period`, `TimeBudget` (`Models/Enums.swift`) are plain Codable Swift enums. `AnswerKind` (also there) has associated values (`.choiceOnly([String])`, `.choiceOrText([String])`) and is used only by the live `QuestionBank` — it is **never** stored directly on a `@Model`. See the gotcha below.
- `CheckIn.photoData: Data?` — one optional photo attached while recording that check-in (see "Photo attachment" below). Backed up like everything else (included in `CheckInDTO`, so it rides along in the encrypted CloudKit backup and the JSON export).
- `CheckIn.taggedPersonName: String?` / `taggedPersonPhoneNumber: String?` — set on an evening check-in when a smile was composed for it during `CheckInFlowView.save()`. Lets Reflect's one-click resend (`ReflectView.sendAnotherSmile`) reuse the same person without re-running `ContactPickerPresenter`. Also included in `CheckInDTO`/the encrypted backup.
- `Smile`: a sent or received smile (`direction: SmileDirection`). Written locally the moment you compose one (`sent`) or the moment a `CKShare` link is accepted (`received`) — see "Smiles" below. Also included in the encrypted backup/export/delete-all flows, same as everything else.

**Important gotcha — don't persist `AnswerKind` directly on a `@Model`.** An earlier version stored `QuestionResponse.answerKind: AnswerKind` directly and it crashed at runtime — `Could not cast value of type 'Swift.Optional<Any>' to 'gratitude.AnswerKind'` — the moment a saved value got faulted back in (e.g. right after a `CheckInFlowView.save()`, when `HomeView`'s `@Query` re-fetches). SwiftData's `@Model` macro doesn't reliably round-trip a Codable enum that carries associated values once it's re-read from the store. The fix in place: `QuestionResponse` persists a plain, no-associated-value `AnswerKindTag` enum (`Models/Enums.swift`) instead, via `AnswerKind.tag`. `AnswerKind` itself stays a pure in-memory type on `Question`. If you're tempted to store a richer enum on a `@Model` again, don't — mirror this pattern (a persisted tag/case + any payload as separate plain properties) instead.

**Second gotcha**: `gratitudeApp.swift`'s `ModelConfiguration` explicitly passes `cloudKitDatabase: .none`. The project's entitlements declare an iCloud/CloudKit container, and if that flag is left at its default, SwiftData auto-enables NSPersistentCloudKitContainer-style automatic mirroring — which requires every attribute to be optional/defaulted and crashes at launch against this schema. This app does *not* use that automatic mirroring; it does its own manual encrypted backup (see below). Don't remove `cloudKitDatabase: .none` without reworking the schema to satisfy CloudKit mirroring's constraints.

### Question bank (`QuestionBank/`)

The actual question content lives in `Resources/questions.json` (bundled resource, auto-copied via the synchronized group — see below), **not** hardcoded in Swift. `QuestionBank.swift` decodes it once into `[Question]` via small private DTOs (`QuestionBankDTO`/`QuestionDTO`) and exposes `QuestionBank.questions(for:budget:)`. This was a deliberate move away from an earlier version that hardcoded the arrays in `MorningQuestions.swift`/`EveningQuestions.swift` (both deleted) — editing question wording/options is now a JSON edit, no rebuild-the-logic required, and `loadBundledQuestions()` is the seam a future remote-config/CloudKit-backed question set would slot into (swap it for a network fetch returning the same decoded shape; nothing above `QuestionBank` would need to change). Deliberately *not* SQLite — the content is a small, rarely-changing nested list, not relational data, so a bundled JSON file is the right amount of machinery, not a database.

In the JSON, `answerKind` is one of the `AnswerKindTag` raw values (`"choiceOnly"`, `"choiceOrText"`, `"textOnly"`, `"scale"`) with an optional `options` array — reusing that persistence-layer tag type here is deliberate, not a coincidence; don't invent a second string enum for the same four cases.

Question `id`s are stable across time budgets on purpose (e.g. `"morning.focus"` exists in the quick, standard, and long morning sets) so evening prompts can look up *that day's* morning answer regardless of which budget was used that morning — see `Question.resolvedPrompt(morningCheckIn:)` and the `{morningFocus}` / `{morningFeeling}` placeholder substitution. If you add a new morning question that an evening prompt should reference, keep its `id` consistent across all three morning budget arrays in the JSON. `QuestionBank.options(forQuestionId:)` reads options back out of the loaded bank (used by `DebugSeeding` for plausible sample answers) — prefer that over duplicating an option list elsewhere.

### Services (`Services/`)

- `CloudBackupService` + `EncryptionKeyStore` + `BackupDTOs`: on-demand (not live-sync) backup. Every `CheckIn` is serialized to a DTO, JSON-encoded, AES-GCM-encrypted with a key from `EncryptionKeyStore` (Keychain, `kSecAttrSynchronizable = true` so it syncs privately via iCloud Keychain, never uploaded itself), then stored as ciphertext in a single `EncryptedEntry` CKRecord type in the user's private CloudKit database. Restore reverses this and de-dupes by id.
- `MemoryEngine`: picks a past day to resurface in Reflect (`HighlightedMemory` — a date plus its morning/evening `CheckIn`s and any photo). A random pick, not a mood match — Reflect doesn't ask how you're feeling (see below) — preferring days where both morning and evening were completed, since those give the fullest picture. `ReflectView` tracks shown dates in `@State` and passes them as `excluding:` so "show me another" doesn't repeat until you've actually seen everything. `HighlightedMemoryView` renders the picked day spotlighted front-and-center (centered date header, hero photo, morning/evening sections stacked) rather than as a row in a list — that's deliberate; don't regress it back to a list/feed layout.
- `PhotoAttachment`: not a permission-gated service — just a pure `UIImage`/`Data` downsizing helper (max ~1200pt, JPEG @0.6) applied to whatever `PhotosPicker` hands back before it's stored on a `CheckIn`. See "Photo attachment" below for why there's no PhotoKit/`PHPhotoLibrary` code anywhere in this app.
- `StreakEngine`: a day only counts toward the streak once **both** morning and evening are done; today doesn't break an existing streak while still in progress (see doc comment).
- `NotificationScheduler` + `NotificationDelegate`: local-only `UNCalendarNotificationTrigger` reminders, two fixed identifiers (`morning-reminder` / `evening-reminder`), rescheduled on time change. Deliberately does **not** use the Push Notifications capability/APNs — reminders are local and the CloudKit backup above is manual pull/push, not push-triggered — so this app can run under a free/Personal Apple Developer team. If `com.apple.developer.icloud-services`/`aps-environment` in the entitlements ever gets a real dependency on remote push, that assumption breaks.
- `AppSettings.swift`: the single source of truth for `UserDefaults` key strings shared between `@AppStorage` in views and plain (non-View) service code. Also has `UserProfile.displayName` (falls back to `UIDevice.current.name`) — the name attached to outgoing Smiles.
- `SmileService`: creates/accepts `CKShare`-backed Smile records — see "Smiles" below. `composeSentSmile(personName:message:senderName:context:)` is the one shared entry point for creating the local `Smile(direction: .sent)` record and preparing the `CKShare` link/message body — both `CheckInFlowView.sendSmile` (first send, from the composer) and `ReflectView.sendAnotherSmile` (one-click resend) call it rather than duplicating the CKShare logic. Add any future "send a smile" entry point through this same helper.
- `PersistenceController`: the single `ModelContainer`, shared between the SwiftUI `App` and `AppDelegate` (which needs its own `ModelContext` to write incoming Smiles from outside the view tree, before any SwiftUI view even exists to hand it one via `@Environment`).
- `DebugSeeding` (`#if DEBUG` only): populates ~2 weeks of realistic sample data through normal SwiftData saves — see "Dev scripts" below. Never runs unless launched with `--seed-sample-data`; a normal Xcode Debug run doesn't silently seed anything.

### Photo attachment — deliberately not Photos-library scanning

Attaching a photo is something you do *while recording* a morning/evening check-in (in `CheckInSummaryView`, via `PhotoAttachmentView`), never something Reflect mode lets you do — Reflect only ever showcases whatever was already attached (`MemoryCardView` renders `MemoryCard.photo`, a plain `UIImage?`, with no picker). This was a deliberate product decision, not just an implementation detail — don't add a photo picker to `ReflectView`.

Photo picking uses SwiftUI's `PhotosPicker` (`PhotosUI`), which runs out-of-process and needs **no system permission at all** — no `NSPhotoLibraryUsageDescription`, no authorization prompt, nothing to accidentally deny. This is why there's no `PHPhotoLibrary`/PhotoKit code anywhere in this app (an earlier version scanned the Photos library by date range and needed contextual permission handling in `ReflectView` — that whole path was removed). If a future feature seems to need broader Photos access than "the one photo the user explicitly picked," push back on that requirement before reaching for PhotoKit.

### Smiles — real cross-device delivery via CloudKit Sharing

Evening check-ins let you tag a response with a contact and send them a "smile" (`SmileComposerView`, only shown for `period == .evening` in `CheckInSummaryView`). This is the one feature that reaches another person's device, and it's built without any custom backend. The person/phone tagged this way is also saved onto the `CheckIn` itself (`taggedPersonName`/`taggedPersonPhoneNumber`), so Reflect can later offer a one-click resend for that same day (`ReflectView.sendAnotherSmile`) without re-running the contact picker — both paths funnel through the same `SmileService.composeSentSmile` helper.

- Delivery always goes out as a plain iMessage (`MessageComposePresenter`), addressed to the contact's phone number, with the message text plus a `CKShare.url` appended (`SmileService.prepareShare`). The `CKShare`'s root record lives in a **custom** CloudKit zone (`SmileZone`) in the private database — sharing requires a custom zone, the default zone can't be shared — with `publicPermission = .readOnly`, so *any* iCloud user with the link can open it. No participant pre-resolution, no contact-to-iCloud-identity matching, no server of our own.
- If the recipient has Gratitude installed and taps the link, iOS routes straight to `AppDelegate.application(_:userDidAcceptCloudKitShareWith:)` — this is *why the app has a UIKit `AppDelegate` at all* despite otherwise being pure SwiftUI (`@UIApplicationDelegateAdaptor` in `gratitudeApp.swift`). That routing is handled natively by CloudKit + the container entitlement; it needs no associated domain, no web hosting, and no Push Notifications capability (accepting a share via a tapped link is a direct OS→delegate callback, not something that needs silent push).
- If the recipient doesn't have the app, the link just doesn't do anything special — but the plain message text sent alongside it still reads as a normal smile/thank-you. There is no way to know in advance whether a given contact has the app installed (it isn't on the App Store), which is why detection isn't attempted — the link degrades gracefully instead.
- **The `Smile` CloudKit records are deliberately unencrypted**, unlike everything in `CloudBackupService`. That's not an oversight: the recipient is a different iCloud account without our AES key, so encrypting would make it unreadable to them. Never put anything in a `SmileService` record beyond the message/sender name itself.
- Untestable solo: accepting a share requires a second iCloud account/device, which isn't available in this environment. What *is* verified (via the `ios-simulator` MCP): the contact picker and message composer present correctly, the local `Smile(direction: .sent)` record is created regardless of whether the CloudKit round-trip succeeds (it degrades gracefully — see `CheckInFlowView.sendSmile` and `ReflectView.sendAnotherSmile`), and `MFMessageComposeViewController.canSendText()` correctly reports `false` in Simulator (no cellular), which is handled with a "Messages isn't available" alert rather than crashing.

**Important gotcha — don't present `CNContactPickerViewController` or `MFMessageComposeViewController` via SwiftUI's `.sheet`.** Both dismiss *themselves* once the user finishes with them. Wrapping either as the content of a `.sheet(isPresented:)` — especially nested inside another sheet, which is the case here since `CheckInFlowView` is itself already presented as a sheet from `HomeView` — causes a desync between the picker's self-dismissal and SwiftUI's binding-driven dismissal. Observed failure mode: selecting a contact silently dismissed the *entire* check-in flow back to Home, discarding an in-progress entry, with no crash and nothing in the crash log (only visible via `log show --predicate 'process == "gratitude"'` showing the Contacts extension scene tearing down normally — the bug is a SwiftUI-level state desync, not a crash). The fix, and the pattern to follow for any future system picker with this self-dismissing behavior: `ModalPresenter` (`Views/Common/`) presents UIKit view controllers directly via the key window's root view controller, bypassing `.sheet` entirely. `ContactPickerPresenter` and `MessageComposePresenter` (both `Views/Common/`) wrap `CNContactPickerViewController`/`MFMessageComposeViewController` this way — each is a small `NSObject` class (not a `View`) held in `@State` on the caller just long enough to retain the delegate, cleared once the callback fires.

### Views

- `HomeView` is the root and owns the day-navigation state (`selectedDate`, defaults to today, can page backward with no lower bound but never forward past today) plus a one-shot `autoLaunchIfNeeded()` (`@State hasAutoLaunched` guards it) that opens straight into the Morning or Evening flow on cold launch if that period (morning = before noon, evening = noon onward) isn't done yet for today. Past days are read-only: a completed day's card pushes `CheckInDetailView`, an incomplete past day's card is disabled — only *today's* incomplete card can start `CheckInFlowView`. Don't reintroduce backfilling past days without checking with the product owner first; it was an explicit, deliberate choice against the app's "answer in the moment" premise. Morning specifically also locks itself once noon passes on *today*, same disabled treatment as a locked past day — `isPastMorningWindow` in `HomeView`, not a separate flag on the model.
- Tapping the date label in `dateNav` opens `CalendarPickerView` (`Views/Home/`) — a hand-built month grid (no `DatePicker`/`MultiDatePicker`, since neither lets you decorate individual days) with a small dot under each day colored by that evening's mood (`Mood.color(for:)`, same ramp as `MoodScaleView`). Only evening check-ins carry a mood rating, so only evening days get a dot. Tapping a day sets `selectedDate` and dismisses; future days are grayed out and untappable, matching Home's own "never forward past today" rule.
- `CheckInFlowView` is a small local state machine over one `[Question]` array resolved once a `TimeBudget` is picked (`stepIndex`: `-1` = budget picker, `0..<count` = a question, `count` = summary), backed by a parallel `[AnswerDraft]` array. `ChipSelectorView` uses the custom `FlowLayout` (a `Layout` conformance, not a `LazyVGrid`) so chip rows wrap based on actual rendered width.
- `Theme.swift` (`Views/Common/`) is the single place semantic colors (`MorningTint`/`EveningTint`/`ReflectTint`/`PositiveTint` — real Asset colorset entries with light+dark variants, not hardcoded `Color(...)`), the mood color ramp, and the haptics helper live. Prefer extending this over adding ad hoc colors in a view.
- Every modal `.sheet` needs its own explicit close affordance (`SettingsView` has a toolbar "Done" bound to `@Environment(\.dismiss)`, `CheckInFlowView`/`ReflectView` have the circular "×") — swipe-to-dismiss alone isn't discoverable enough; this was a real usability complaint, not a hypothetical.

### Concurrency

The project sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so every type in this module (views, services, DTOs) is MainActor-isolated by default unless marked otherwise — there's no need to sprinkle `@MainActor` everywhere. One sharp edge this causes: passing a MainActor-isolated initializer as a bare function reference into a synchronous higher-order function (e.g. `checkIns.map(CheckInDTO.init)`) triggers a concurrency warning, because the bare reference loses the "runs in the caller's isolation" inference a closure literal gets. Use an explicit closure instead: `checkIns.map { CheckInDTO(from: $0) }`.

### Dev scripts (`Scripts/`)

- `Scripts/seed-simulator.sh [--build] [--reset] [--simulator NAME]` — installs the last Debug build (or builds first with `--build`) and launches it with `--seed-sample-data` (and `--reset-data` if `--reset` is passed), which `DebugSeeding` picks up. Real SwiftData writes, not raw SQLite — safe to rerun any time the schema changes.
- `Scripts/reset-simulator.sh [--simulator NAME]` — uninstalls the app for a true clean slate (SwiftData store, Keychain, everything), distinct from `seed-simulator.sh --reset`'s in-place wipe-and-reseed.
- Both scripts are plain ASCII on purpose (no em dashes/smart punctuation) — an earlier version used them in `echo` strings and hit a shell parse error (`unbound variable` on a mangled token) that disappeared once the non-ASCII characters were removed. Keep new script output ASCII-only.
- `xcrun simctl launch <udid> <bundle-id> <extra-args...>` passes `<extra-args...>` straight through to the process as `ProcessInfo.processInfo.arguments` — that's the whole mechanism, no custom IPC.

### Signing / entitlements

`gratitude.entitlements` declares an iCloud/CloudKit container (`iCloud.com.sachabest.gratitude`). If Xcode's capability editor is used to touch this again, double check it didn't collapse the container array into a single malformed `<string>` with newline-joined duplicates (it's done this before) — the array should contain exactly one clean `<string>` element.

That one container backs two independent CloudKit uses now — `CloudBackupService`'s encrypted private-database backup, and `SmileService`'s shared-zone Smiles — with distinct record types (`EncryptedEntry` vs `Smile`) and, for sharing, a distinct custom zone. Neither needs Push Notifications capability; keep it that way (see `NotificationScheduler`'s doc comment on why staying push-free matters for signing).

When touching `CKShare.Metadata`, use `hierarchicalRootRecordID` (`AppDelegate`, `SmileService.acceptShare`), not `rootRecordID` — the latter is deprecated since iOS 16 and returns an implicitly-unwrapped value that Xcode will warn about.

### CI (`.github/workflows/`)

`build.yml` and `test.yml` both run on `macos-15`, select whatever Xcode `latest-stable` resolves to (`maxim-lobanov/setup-xcode`), and target `platform=iOS Simulator,name=iPhone 17` with `CODE_SIGNING_ALLOWED=NO` — that flag is required, not cosmetic: the project's `DEVELOPMENT_TEAM`/`CODE_SIGN_STYLE=Automatic` are tied to a local Xcode account that doesn't exist on a CI runner, and simulator builds don't need real signing anyway. If a runner image doesn't yet carry an "iPhone 17" simulator (very new device name), adjust the destination in both workflows — same failure mode as `Scripts/seed-simulator.sh`'s destination lookup, unrelated fix locations. `test.yml` runs whatever's in `gratitudeTests`/`gratitudeUITests` today (the template stubs) and needs no changes as real tests are added.
