# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Gratitude is a personal iPhone app (SwiftUI + SwiftData) for a twice-daily mindfulness check-in: a short adaptive Q&A right after waking and right before bed, plus an on-demand "Reflect" mode that resurfaces a specific past day (morning and evening together, plus any photo) to revisit, spotlighted front-and-center rather than as a list. Local-first storage, with an optional client-side-encrypted backup to the user's own private CloudKit database. Evening check-ins also let you tag a response with a person and send them a "Smile" ("send a smile" is the app's verbiage throughout) — the one feature in this app that involves another person's device (see "Smiles" below). If that day's evening check-in had a tagged person, Reflect offers a one-click resend of the same smile without re-running the contact picker. See `README.md` for the product/setup overview.

## Commands

Build for the simulator from the CLI (no test target is wired up with real tests yet — `gratitudeTests`/`gratitudeUITests` are unmodified Xcode template stubs):

```bash
# List available simulators (needed once to get a destination id/name)
xcrun simctl list devices available

# Build
xcodebuild -project ios/gratitude.xcodeproj -scheme gratitude \
  -destination 'platform=iOS Simulator,id=<SIMULATOR-ID>' build

# Install + launch after a build, to sanity-check it boots
xcrun simctl install <SIMULATOR-ID> <path-to>/gratitude.app
xcrun simctl launch <SIMULATOR-ID> com.sachabest.gratitude
xcrun simctl io <SIMULATOR-ID> screenshot out.png
```

The repo root also holds `smiles-worker/` (a Cloudflare Worker, not an Xcode target — see the "Smiles" section below and its own README) and `mcp/idb/` (tooling for the MCP server described next) alongside the `ios/` Xcode project — none of the three affect each other's build/deploy paths.

This repo also has the `ios-simulator` MCP server configured (`.mcp.json`, at the repo root so Claude Code and other MCP-aware tools auto-discover it) for interactive testing — screenshotting, tapping, typing, swiping through real flows instead of only reading code. Its `ui_tap`/`ui_swipe`/`ui_type`/`ui_describe_all` tools need Facebook's `idb` client on `PATH`; see README.md's "Interactive Simulator testing" section for how it's set up (`idb-companion` via Homebrew, `idb` itself pinned in `mcp/idb/` via `uv`, symlinked onto `PATH`). Always pull tap coordinates from `ui_describe_all`'s `AXFrame` (already in the same point-space `ui_tap` expects) rather than eyeballing a screenshot — screenshots are pixel space at a different scale (e.g. 1206×2622 px vs. 402×874 pt on iPhone 17) and guessed coordinates miss.

The `gratitude` folder (under `ios/`) is a **PBXFileSystemSynchronizedRootGroup** in the Xcode project — any `.swift` file added anywhere under `ios/gratitude/gratitude/` is automatically picked up by the target. Never hand-edit `project.pbxproj` to add source files.

## Architecture

### Data model (SwiftData, `Models/`)

- `CheckIn`: one morning or evening entry for a given calendar day. `date` is always normalized to `Calendar.current.startOfDay(for:)` — every date comparison in the codebase (today lookups, streaks, the date-nav header) relies on comparing already-normalized `Date` values with plain `==`, not calendar-aware equality checks.
- `QuestionResponse`: one answer, cascade-deleted with its `CheckIn`. Stores a *snapshot* of the question text and `answerKindTag` at the time it was answered, independent of the live `QuestionBank` content, so past entries stay legible even if question wording changes later.
- `Period`, `TimeBudget` (`Models/Enums.swift`) are plain Codable Swift enums. `AnswerKind` (also there) has associated values (`.choiceOnly([String])`, `.choiceOrText([String])`) and is used only by the live `QuestionBank` — it is **never** stored directly on a `@Model`. See the gotcha below.
- `CheckIn.photoData: Data?` — one optional photo attached while recording that check-in (see "Photo attachment" below). Backed up like everything else (included in `CheckInDTO`, so it rides along in the encrypted CloudKit backup and the JSON export).
- `CheckIn.taggedPersonName: String?` / `taggedPersonPhoneNumber: String?` — set on an evening check-in when a smile was composed for it during `CheckInFlowView.save()`. Lets Reflect's one-click resend (`ReflectView.sendAnotherSmile`) reuse the same person without re-running `ContactPickerPresenter`. Also included in `CheckInDTO`/the encrypted backup.
- `Smile`: a sent or received smile (`direction: SmileDirection`). Written locally the moment you compose one (`sent`) or the moment a `CKShare` link is accepted (`received`) — see "Smiles" below. Also included in the encrypted backup/export/delete-all flows, same as everything else.

**Important gotcha — don't persist `AnswerKind` directly on a `@Model`.** An earlier version stored `QuestionResponse.answerKind: AnswerKind` directly and it crashed at runtime — `Could not cast value of type 'Swift.Optional<Any>' to 'gratitude.AnswerKind'` — the moment a saved value got faulted back in (e.g. right after a `CheckInFlowView.save()`, when `HomeView`'s `@Query` re-fetches). SwiftData's `@Model` macro doesn't reliably round-trip a Codable enum that carries associated values once it's re-read from the store. The fix in place: `QuestionResponse` persists a plain, no-associated-value `AnswerKindTag` enum (`Models/Enums.swift`) instead, via `AnswerKind.tag`. `AnswerKind` itself stays a pure in-memory type on `Question`. If you're tempted to store a richer enum on a `@Model` again, don't — mirror this pattern (a persisted tag/case + any payload as separate plain properties) instead.

**Second gotcha**: `gratitudeApp.swift`'s `ModelConfiguration` explicitly passes `cloudKitDatabase: .none`. The project's entitlements declare an iCloud/CloudKit container, and if that flag is left at its default, SwiftData auto-enables NSPersistentCloudKitContainer-style automatic mirroring — which requires every attribute to be optional/defaulted and crashes at launch against this schema. This app does *not* use that automatic mirroring; it does its own manual encrypted backup (see below). Don't remove `cloudKitDatabase: .none` without reworking the schema to satisfy CloudKit mirroring's constraints.

### Question bank (`QuestionBank/`)

The actual question content lives in `Resources/questions.json` (bundled resource, auto-copied via the synchronized group — see below), **not** hardcoded in Swift. `QuestionBank.swift` decodes it once into `[Question]` via small private DTOs (`QuestionBankDTO`/`QuestionDTO`) and exposes `QuestionBank.questions(for:budget:)`. This was a deliberate move away from an earlier version that hardcoded the arrays in `MorningQuestions.swift`/`EveningQuestions.swift` (both deleted) — editing question wording/options is now a JSON edit, no rebuild-the-logic required, and `loadBundledQuestions()` is the seam a future remote-config/CloudKit-backed question set would slot into (swap it for a network fetch returning the same decoded shape; nothing above `QuestionBank` would need to change). Deliberately *not* SQLite — the content is a small, rarely-changing nested list, not relational data, so a bundled JSON file is the right amount of machinery, not a database.

In the JSON, `answerKind` is one of the `AnswerKindTag` raw values (`"choiceOnly"`, `"choiceOrText"`, `"textOnly"`, `"scale"`) with an optional `options` array — reusing that persistence-layer tag type here is deliberate, not a coincidence; don't invent a second string enum for the same four cases.

Question `id`s are stable across time budgets on purpose (e.g. `"morning.focus"` exists in the quick, standard, and long morning sets) so evening prompts can look up *that day's* morning answer regardless of which budget was used that morning — see `Question.resolvedPrompt(morningCheckIn:)` and the `{morningFocus}` / `{morningFeeling}` placeholder substitution. If you add a new morning question that an evening prompt should reference, keep its `id` consistent across all three morning budget arrays in the JSON. `QuestionBank.options(forQuestionId:)` reads options back out of the loaded bank (used by `DebugSeeding` for plausible sample answers) — prefer that over duplicating an option list elsewhere.

### Services (`Services/`)

- `CloudBackupService` + `EncryptionKeyStore` + `BackupDTOs`: on-demand (not live-sync) backup. Every `CheckIn` is serialized to a DTO, JSON-encoded, AES-GCM-encrypted with a key from `EncryptionKeyStore` (Keychain, `kSecAttrSynchronizable = true` so it syncs privately via iCloud Keychain, never uploaded itself), then stored as ciphertext in a single `EncryptedEntry` CKRecord type in the user's private CloudKit database. Restore reverses this and de-dupes by id.
- `MemoryEngine`: picks a past day to resurface in Reflect (`HighlightedMemory` — a date plus its morning/evening `CheckIn`s and any photo). A random pick, not a mood match — Reflect doesn't ask how you're feeling (see below) — preferring days where both morning and evening were completed, since those give the fullest picture. `ReflectView` tracks shown dates in `@State` and passes them as `excluding:` so "show me another" doesn't repeat until you've actually seen everything. `HighlightedMemoryView` renders the picked day spotlighted front-and-center (centered date header, hero photo, morning/evening sections stacked) rather than as a row in a list — that's deliberate; don't regress it back to a list/feed layout.
- `PhotoAttachment`: not a permission-gated service — just a pure `UIImage`/`Data` downsizing helper (max ~1200pt, JPEG @0.6) applied to whatever `PhotosPicker` hands back before it's stored on a `CheckIn`. See "Photo attachment" below for why there's no PhotoKit/`PHPhotoLibrary` code anywhere in this app.
- `StreakEngine`: a day only counts toward the streak once **both** morning and evening are done; today doesn't break an existing streak while still in progress (see doc comment).
- `NotificationScheduler` + `NotificationDelegate`: local-only `UNCalendarNotificationTrigger` reminders, two fixed identifiers (`morning-reminder` / `evening-reminder`), rescheduled on time change. Doesn't use the Push Notifications capability/APNs itself — reminders are local and the CloudKit backup above is manual pull/push, not push-triggered — that capability is `SmileService`'s alone now (see "Smiles" below and the entitlements section), on a paid Apple Developer account that no longer needs to stay push-free the way an earlier, free/Personal-team version of this project did.
- `AppSettings.swift`: the single source of truth for `UserDefaults` key strings shared between `@AppStorage` in views and plain (non-View) service code. Also has `UserProfile.displayName` (falls back to `UIDevice.current.name`) — the name attached to outgoing Smiles.
- `SmileService`: creates/accepts `CKShare`-backed Smile records — see "Smiles" below. Split into two calls, deliberately not one: `prepareMessage(message:senderName:)` prepares the `CKShare` link/message body only (no SwiftData writes), and `recordSent(personName:message:cloudRecordName:context:)` creates the local `Smile(direction: .sent)` record — callers must only invoke `recordSent` from a `MessageComposePresenter`'s `onFinish` callback gated on `result == .sent`, never merely after composing, or cancelling out of the Messages sheet would still log a "sent" smile (and, for the ad-hoc path, burn a rate-limited send that never went anywhere) — a real bug fixed once already, don't reintroduce it by re-merging the two calls. `CheckInFlowView.sendSmile` (first send, from the composer), `ReflectView.sendAnotherSmile` (one-click resend), and `AdHocSmileComposerView.send` (send anytime, from the Smiles log) all call both rather than duplicating the CKShare logic. Add any future "send a smile" entry point through these same two helpers.
- `AppConfigService`: fetches a single well-known record from the container's **public** CloudKit database (`AppConfig-main`) as lightweight remote config, editable directly in CloudKit Console without a build. Currently backs `AdHocSmileLimiter.cachedWeeklyLimit` only. See the "Smiles" section below.
- `PersistenceController`: the single `ModelContainer`, shared between the SwiftUI `App` and `AppDelegate` (which needs its own `ModelContext` to write incoming Smiles from outside the view tree, before any SwiftUI view even exists to hand it one via `@Environment`).
- `DebugSeeding` (`#if DEBUG` only): populates ~2 weeks of realistic sample data through normal SwiftData saves — see "Dev scripts" below. Never runs unless launched with `--seed-sample-data`; a normal Xcode Debug run doesn't silently seed anything.
- `DebugActions` (`#if DEBUG` only): one-off diagnostic actions behind their own launch flags, same mechanism as `DebugSeeding` but for isolated repro rather than sample data — currently just `--test-send-smile` (see the CloudKit gotcha below).

### Photo attachment — deliberately not Photos-library scanning

Attaching a photo is something you do *while recording* a morning/evening check-in (in `CheckInSummaryView`, via `PhotoAttachmentView`), never something Reflect mode lets you do — Reflect only ever showcases whatever was already attached (`MemoryCardView` renders `MemoryCard.photo`, a plain `UIImage?`, with no picker). This was a deliberate product decision, not just an implementation detail — don't add a photo picker to `ReflectView`.

Photo picking uses SwiftUI's `PhotosPicker` (`PhotosUI`), which runs out-of-process and needs **no system permission at all** — no `NSPhotoLibraryUsageDescription`, no authorization prompt, nothing to accidentally deny. This is why there's no `PHPhotoLibrary`/PhotoKit code anywhere in this app (an earlier version scanned the Photos library by date range and needed contextual permission handling in `ReflectView` — that whole path was removed). If a future feature seems to need broader Photos access than "the one photo the user explicitly picked," push back on that requirement before reaching for PhotoKit.

### Smiles — real cross-device delivery via CloudKit Sharing

Evening check-ins let you tag a response with a contact and send them a "smile" (`SmileComposerView`, only shown for `period == .evening` in `CheckInSummaryView`). This is the one feature that reaches another person's device, and it's built without any custom backend. The person/phone tagged this way is also saved onto the `CheckIn` itself (`taggedPersonName`/`taggedPersonPhoneNumber`), so Reflect can later offer a one-click resend for that same day (`ReflectView.sendAnotherSmile`) without re-running the contact picker — both paths, plus the ad-hoc composer (below), funnel through the same `SmileService.prepareMessage`/`recordSent` helpers.

- **Sending one anytime**: the "+" in `SmilesView`'s toolbar opens `AdHocSmileComposerView` — the same contact/message composer, but not tied to a check-in. Deliberately rate-limited (`AdHocSmileLimiter`, per calendar week — the smile-tag-during-check-in and Reflect-resend paths aren't limited, since both are already naturally bounded by real journal activity) so it stays an occasional gesture rather than something to spam. The weekly limit itself is fetched from `AppConfigService` — a single well-known record (`AppConfig-main`) in the CloudKit container's **public** database, editable directly in CloudKit Console's Public Data tab with no app update needed (an `adHocSmileWeeklyLimit` Int64 field). Public database reads don't require iCloud sign-in, so this works even before/without it. Like everything CloudKit here, that record needs to exist in **both** Development and Production to matter in both places (see the schema gotcha right below) — until it exists, or a fetch fails, the app just keeps whatever was last cached, or `AdHocSmileLimiter`'s built-in default of 3/week.

- Delivery always goes out as a plain iMessage (`MessageComposePresenter`), addressed to the contact's phone number, with the message text plus a link (`SmileService.prepareMessage`/`landingURL`). That link is **not** the raw `CKShare.url` — it's `https://gratitude.sachabest.com/s?u=<CKShare URL>&from=<sender name>`, a page hosted by a small Cloudflare Worker (`smiles-worker/` at the repo root — not part of the Xcode project; auto-deployed by `.github/workflows/deploy-smiles-worker.yml` on push to `main` when that directory changes, via a `CLOUDFLARE_API_TOKEN` repo secret — see `smiles-worker/README.md` for one-time setup). Wrapping it this way does two things a raw `icloud.com` link couldn't: iMessage's own link-preview fetcher reads that page's Open Graph tags and renders a branded "X sent you a Smile" card instead of a plain blue link, and a recipient who opens it without the app gets a real "Get Gratitude" page instead of a dead end. The `CKShare`'s root record itself still lives in a **custom** CloudKit zone (`SmileZone`) in the private database — sharing requires a custom zone, the default zone can't be shared — with `publicPermission = .readOnly`, so *any* iCloud user with the reconstructed URL can still open it. This wrapped link is the one guaranteed delivery path and works for any recipient regardless of whether they've used Gratitude before.
- On top of that link, `prepareShare` also tries `findParticipant(phoneNumber:)` — a `CKFetchShareParticipantsOperation` phone-number discoverability lookup — and if it resolves, adds that person as a real `CKShare.Participant` (`.readOnly`) on the *same* share before saving. When it resolves (recipient has "Discoverable by Others" on in their iCloud settings, phone number matches their Apple ID exactly, and they already have Gratitude installed), CloudKit's own infrastructure delivers a native "A Smile from X" push invitation — no server, no APNs credentials, no device-token handling of ours involved (see `AppDelegate`'s doc comment). This is strictly additive and silently best-effort: it fails far more often than it succeeds in practice (most people don't have iCloud discoverability on), and failure is intentionally swallowed (`findParticipant` just returns `nil`) since the wrapped link is what actually has to carry the message regardless.
- **Two convergent acceptance entry points, both funneling into `SmileService.acceptShareAndSaveSmile`**: (1) `AppDelegate.application(_:userDidAcceptCloudKitShareWith:)` — the native path, fired by tapping a raw `icloud.com` link directly or by the discoverable-participant push invitation above; (2) `AppDelegate.application(_:continue:restorationHandler:)` — fired by tapping the `gratitude.sachabest.com` link when the app is already installed (a Universal Link, via the Associated Domains entitlement + that domain's `apple-app-site-association`, served by the Cloudflare Worker). Unlike a raw `icloud.com` link, iOS doesn't recognize our own domain as a CloudKit share on its own, so this handler pulls the `u` query item back out and calls `SmileService.fetchShareMetadata(from:)` (a `CKFetchShareMetadataOperation`, mirroring `findParticipant`'s operation-based style) before accepting — everything after that is identical between the two paths. Whichever fires, the resulting `Smile(direction: .received, hasBeenSeen: false)` triggers `HomeView`'s `@Query`-driven `SmileReceivedView` hero screen (`Views/Smiles/SmileReceivedView.swift`) the next time the app is on screen — no visible CKShare/share-accept chrome, just the smile.
- If the recipient doesn't have the app: the native path can't reach them at all (no device to push to, no app to route a raw link into), but the `gratitude.sachabest.com` link *can* — Universal Links only intercept when the app is installed, so everyone else's tap just loads that page in Safari, showing the Worker's "Get Gratitude" fallback with an install link. There's no true zero-tap deferred deep linking after that install (verified: this isn't an App-Store-vs-TestFlight distinction, Apple simply doesn't offer automatic post-install URL redelivery without a third-party attribution SDK, which was deliberately ruled out as disproportionate for this app) — the same link is still sitting in the same Messages thread, so tapping it again once the app exists is a normal Universal Link straight into `SmileReceivedView`. One extra, obvious tap, no new dependency.
- **The `Smile` CloudKit records are deliberately unencrypted**, unlike everything in `CloudBackupService`. That's not an oversight: the recipient is a different iCloud account without our AES key, so encrypting would make it unreadable to them. Never put anything in a `SmileService` record beyond the message/sender name itself. The smile's actual message text never appears in the `gratitude.sachabest.com` URL either — only the sender's display name does, for preview purposes; the Worker has no CloudKit access at all.
- Untestable solo: accepting a share, and especially confirming the discoverable-participant push path above actually fires, requires two real iCloud accounts/devices (one with "Discoverable by Others" on), which isn't available in this environment. What *is* verified (via the `ios-simulator` MCP and `DebugActions`' `--seed-unseen-smile` flag): the contact picker and message composer present correctly, the local `Smile(direction: .sent)` record is created only once `MFMessageComposeViewController` reports `.sent` (see the second incident write-up below — it used to be created unconditionally, which was a real bug), `MFMessageComposeViewController.canSendText()` correctly reports `false` in Simulator (no cellular) and is handled with an alert rather than crashing, and `SmileReceivedView` pops correctly (with the right priority against `HomeView`'s check-in auto-launch — see that view's `autoLaunchIfNeeded` doc comment) for a seeded unseen received smile. The Universal Link round-trip and the Worker itself need a real device and a live `gratitude.sachabest.com` — see `smiles-worker/README.md`.

**Important gotcha — CloudKit Development vs. Production schema.** Every CloudKit container has two completely separate environments: **Development** (what a Debug build talks to, whether Simulator or a real device run from Xcode) and **Production** (what a TestFlight or App Store build talks to — determined by the provisioning profile/signing, not the Debug/Release build setting). Development auto-creates record types/zones the first time a save actually succeeds; Production never does — it starts empty and only gets schema (the `Smile` record type, the `SmileZone` custom zone, same for `CloudBackupService`'s `EncryptedEntry`) once someone explicitly clicks **Deploy Schema Changes to Production** in the CloudKit Console (icloud.developer.apple.com → the container → Schema). `AppConfig` (the ad-hoc smile limit's public-database record, above) needs the same treatment, but the other direction matters too since it's manually created rather than auto-created by a save: create the `AppConfig-main` record with its `adHocSmileWeeklyLimit` field once in **each** environment separately (Console's environment picker), or the value one of them sees will just be the built-in default. Skip that step and every real (TestFlight/App Store) build fails every CloudKit save — silently, because `prepareMessage`'s catch block is a deliberate best-effort fallback (see below), so the sender just sees an ordinary text message with no link and no visible error.

This was a real incident: Smiles appeared to "just work" during development because the only verification was that the local fallback `Smile` record got created, never that the CloudKit round-trip itself succeeded (Simulator testing wasn't signed into a real iCloud account). It was only confirmed working — and the `Smile`/`SmileZone` schema first appeared in Development at all — once tested on a real, iCloud-signed-in device. The fix was deploying that schema to Production. If this is suspected again: `Logger(subsystem: "com.sachabest.gratitude", category: "SmileService")` calls at the two swallow points in `SmileService` (`prepareMessage`'s catch, `acceptShare`'s guard/catch) surface the actual `CKError` via Console.app or `log stream --predicate 'subsystem == "com.sachabest.gratitude"'` against a real device. `DebugActions.swift` (`#if DEBUG`, alongside `DebugSeeding`) also has a `--test-send-smile` launch flag that fires `SmileService.prepareMessage` in isolation with throwaway data (deliberately not `recordSent`, since there's no real Messages send to gate it on) — no need to redo a real check-in to reach the composer — useful together with `xcrun devicectl device install app`/`device process launch --console <bundle-id> --test-send-smile` for a fast build-install-launch-observe loop against a real device without touching Xcode's GUI.

**Second real incident, same feature area** — after the CloudKit fix above shipped and the app was live: (1) `AdHocSmileComposerView`/`CheckInFlowView`/`ReflectView` all called what was then a single `composeSentSmile` (CKShare prep + local `Smile` insert, for the ad-hoc path also `AdHocSmileLimiter.recordSend()`) *before* presenting `MFMessageComposeViewController` — so cancelling out of the Messages sheet still logged a "sent" smile and (ad-hoc) burned a weekly slot for a message that never went anywhere; (2) the "Messages isn't available" fallback alert claimed "your smile was saved" when nothing should have been. Fixed by splitting the one call into `prepareMessage` (no SwiftData writes) and `recordSent` (only called from `onFinish` gated on `result == .sent`) — see the `SmileService` bullet above. Keep that split; don't re-merge them to "simplify."

**Important gotcha — don't present `CNContactPickerViewController` or `MFMessageComposeViewController` via SwiftUI's `.sheet`.** Both dismiss *themselves* once the user finishes with them. Wrapping either as the content of a `.sheet(isPresented:)` — especially nested inside another sheet, which is the case here since `CheckInFlowView` is itself already presented as a sheet from `HomeView` — causes a desync between the picker's self-dismissal and SwiftUI's binding-driven dismissal. Observed failure mode: selecting a contact silently dismissed the *entire* check-in flow back to Home, discarding an in-progress entry, with no crash and nothing in the crash log (only visible via `log show --predicate 'process == "gratitude"'` showing the Contacts extension scene tearing down normally — the bug is a SwiftUI-level state desync, not a crash). The fix, and the pattern to follow for any future system picker with this self-dismissing behavior: `ModalPresenter` (`Views/Common/`) presents UIKit view controllers directly via the key window's root view controller, bypassing `.sheet` entirely. `ContactPickerPresenter` and `MessageComposePresenter` (both `Views/Common/`) wrap `CNContactPickerViewController`/`MFMessageComposeViewController` this way — each is a small `NSObject` class (not a `View`) held in `@State` on the caller just long enough to retain the delegate, cleared once the callback fires.

### Views

- `HomeView` is the root and owns the day-navigation state (`selectedDate`, defaults to today, can page backward with no lower bound but never forward past today) plus a one-shot `autoLaunchIfNeeded()` (`@State hasAutoLaunched` guards it) that opens straight into whichever of Morning/Evening currently has an *open* window and isn't done yet for today — if neither window is open right now, it launches to plain Home instead of guessing. Past days are read-only: a completed day's card pushes `CheckInDetailView`, an incomplete past day's card is disabled — only *today's* incomplete card can start `CheckInFlowView`. Don't reintroduce backfilling past days without checking with the product owner first; it was an explicit, deliberate choice against the app's "answer in the moment" premise.

  Both Morning and Evening are also time-windowed, not just "available all day until done": each has a configurable opens/closes time (`Settings/SettingsView.swift`'s "Morning window"/"Evening window" sections, `@AppStorage` keys in `SettingsKeys.morning/eveningWindowStart/End`, defaulting to 4am-11am and 8pm-2am via `CheckInWindowDefaults`). `CheckInWindow.state(start:end:now:)` (`Services/AppSettings.swift`) is the single pure function both `HomeView` and `SettingsView` build on — it returns `.tooEarly`/`.open`/`.tooLate`, and handles the evening window's overnight wrap (`start > end`, e.g. 8pm-2am) by treating `secondsSinceMidnight >= start OR < end` as open, which also means the wrap case never actually surfaces `.tooLate`: the transition from "open" to "closed" for that window coincides with the calendar day rolling over (handled by `HomeView`'s existing day-rollover fix), so by the time the window would close, "today" has already become the next day with a fresh `.tooEarly` state. Don't add a distinct "missed the evening window" message for that reason — there's no observable moment for it. `HomeView` reads the four `@AppStorage` values itself (not by reaching into `CheckInWindow`, which deliberately takes them as parameters rather than reading `UserDefaults` directly) so it stays reactive to Settings changes like everything else in this codebase.
- Tapping the date label in `dateNav` opens `CalendarPickerView` (`Views/Home/`) — a hand-built month grid (no `DatePicker`/`MultiDatePicker`, since neither lets you decorate individual days) with a small dot under each day colored by that evening's mood (`Mood.color(for:)`, same ramp as `MoodScaleView`). Only evening check-ins carry a mood rating, so only evening days get a dot. Tapping a day sets `selectedDate` and dismisses; future days are grayed out and untappable, matching Home's own "never forward past today" rule.
- `CheckInFlowView` is a small local state machine over one `[Question]` array resolved once a `TimeBudget` is picked (`stepIndex`: `-1` = budget picker, `0..<count` = a question, `count` = summary), backed by a parallel `[AnswerDraft]` array. `ChipSelectorView` uses the custom `FlowLayout` (a `Layout` conformance, not a `LazyVGrid`) so chip rows wrap based on actual rendered width.
- `Theme.swift` (`Views/Common/`) is the single place semantic colors (`MorningTint`/`EveningTint`/`ReflectTint`/`PositiveTint` — real Asset colorset entries with light+dark variants, not hardcoded `Color(...)`), the mood color ramp, and the haptics helper live. Prefer extending this over adding ad hoc colors in a view.
- Every modal `.sheet` needs its own explicit close affordance (`SettingsView` has a toolbar "Done" bound to `@Environment(\.dismiss)`, `CheckInFlowView`/`ReflectView` have the circular "×") — swipe-to-dismiss alone isn't discoverable enough; this was a real usability complaint, not a hypothetical.

### Concurrency

The project sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so every type in this module (views, services, DTOs) is MainActor-isolated by default unless marked otherwise — there's no need to sprinkle `@MainActor` everywhere. One sharp edge this causes: passing a MainActor-isolated initializer as a bare function reference into a synchronous higher-order function (e.g. `checkIns.map(CheckInDTO.init)`) triggers a concurrency warning, because the bare reference loses the "runs in the caller's isolation" inference a closure literal gets. Use an explicit closure instead: `checkIns.map { CheckInDTO(from: $0) }`.

### Dev scripts (`ios/Scripts/`)

- `ios/Scripts/seed-simulator.sh [--build] [--reset] [--simulator NAME]` — installs the last Debug build (or builds first with `--build`) and launches it with `--seed-sample-data` (and `--reset-data` if `--reset` is passed), which `DebugSeeding` picks up. Real SwiftData writes, not raw SQLite — safe to rerun any time the schema changes. Uses `cd "$(dirname "$0")/.."` to resolve `gratitude.xcodeproj` relative to itself, so it doesn't care that `ios/` isn't the repo root.
- `ios/Scripts/reset-simulator.sh [--simulator NAME]` — uninstalls the app for a true clean slate (SwiftData store, Keychain, everything), distinct from `seed-simulator.sh --reset`'s in-place wipe-and-reseed.
- Both scripts are plain ASCII on purpose (no em dashes/smart punctuation) — an earlier version used them in `echo` strings and hit a shell parse error (`unbound variable` on a mangled token) that disappeared once the non-ASCII characters were removed. Keep new script output ASCII-only.
- `xcrun simctl launch <udid> <bundle-id> <extra-args...>` passes `<extra-args...>` straight through to the process as `ProcessInfo.processInfo.arguments` — that's the whole mechanism, no custom IPC.

### Signing / entitlements

`gratitude.entitlements` declares an iCloud/CloudKit container (`iCloud.com.sachabest.gratitude`). If Xcode's capability editor is used to touch this again, double check it didn't collapse the container array into a single malformed `<string>` with newline-joined duplicates (it's done this before) — the array should contain exactly one clean `<string>` element. It **does** declare `aps-environment: development` — re-added deliberately (see below), not template leftover this time; if Xcode's capability editor touches this again, confirm it's still there and still resolves to `production` on an Archive/TestFlight build (driven by the provisioning profile, same as everything else CloudKit-environment-related in this file). It also declares `com.apple.developer.associated-domains: ["applinks:gratitude.sachabest.com"]` — Universal Links for the "Smiles" landing page (see above); this needs Xcode's Signing & Capabilities "Associated Domains" capability actually toggled on locally at least once (same paid-account requirement as Push Notifications) for the provisioning profile to include it, or a real-device/TestFlight build will fail to codesign with this entitlement present.

`Info.plist` sets `ITSAppUsesNonExemptEncryption = false` — this app only uses CryptoKit's standard AES-GCM (via `EncryptionKeyStore`/`CloudBackupService`) to protect the user's own data, never a proprietary algorithm or anything sold/marketed as encryption, so it qualifies for the standard export-compliance exemption. This key skips App Store Connect's export-compliance questionnaire on every TestFlight/App Store upload. An earlier version of this file also had `UIBackgroundModes: [remote-notification]` and the entitlements had `aps-environment: development` — both were leftover from the original Xcode CloudKit project template and were removed once TestFlight distribution surfaced them as dead config worth cleaning up before shipping a build. `aps-environment` came back later, deliberately, for `SmileService`'s discoverable-participant push (see "Smiles" above) — `UIBackgroundModes: [remote-notification]` deliberately did **not** come back with it: that flag is for *silent* background pushes, and a `CKShare` invitation is a normal visible alert push the OS handles on its own, so no background-fetch entry point is needed. If a future feature needs a genuine silent/background CloudKit push (e.g. a `CKSubscription` for something other than share invitations), that's the point to reconsider adding it back.

That one container backs two independent CloudKit uses now — `CloudBackupService`'s encrypted private-database backup, and `SmileService`'s shared-zone Smiles — with distinct record types (`EncryptedEntry` vs `Smile`) and, for sharing, a distinct custom zone. `SmileService` is now the one thing in this app that uses the Push Notifications capability, narrowly, for the reason above — `CloudBackupService` and `NotificationScheduler`'s local reminders still don't touch it at all.

When touching `CKShare.Metadata`, use `hierarchicalRootRecordID` (`AppDelegate`, `SmileService.acceptShare`), not `rootRecordID` — the latter is deprecated since iOS 16 and returns an implicitly-unwrapped value that Xcode will warn about.

### CI (`.github/workflows/`)

`build.yml` and `test.yml` both run on `macos-15`, select whatever Xcode `latest-stable` resolves to (`maxim-lobanov/setup-xcode`), point `-project` at `ios/gratitude.xcodeproj`, and target `platform=iOS Simulator,name=iPhone 17` with `CODE_SIGNING_ALLOWED=NO` — that flag is required, not cosmetic: the project's `DEVELOPMENT_TEAM`/`CODE_SIGN_STYLE=Automatic` are tied to a local Xcode account that doesn't exist on a CI runner, and simulator builds don't need real signing anyway. If a runner image doesn't yet carry an "iPhone 17" simulator (very new device name), adjust the destination in both workflows — same failure mode as `ios/Scripts/seed-simulator.sh`'s destination lookup, unrelated fix locations. `test.yml` runs whatever's in `gratitudeTests`/`gratitudeUITests` today (the template stubs) and needs no changes as real tests are added.

`deploy-smiles-worker.yml` is unrelated to the app build — it runs on `ubuntu-latest`, triggers only on pushes to `main` touching `smiles-worker/**`, and deploys via `cloudflare/wrangler-action` using a `CLOUDFLARE_API_TOKEN` repo secret (see `smiles-worker/README.md`). It doesn't touch Xcode/CocoaPods/signing at all.
